# A StarFive VisionFive 2 (JH7110), Imagination PowerVR B-Series BXE-4-32,
# Vulkan 1.3.225 through Imagination's own driver, release build, no heatsink
# fitted, 46.0 C before and 50.5 C after, desktop stopped, all four governors
# pinned to performance, load 0.19.
#
#   cargo xtask bench --skip softpipe --skip gles --check tests/bench-baselines/visionfive-2-powervr.txt
#
# `--skip softpipe` and not `--skip llvmpipe`: this image's software driver calls
# itself softpipe, and the skip matches on any part of the name a device gives
# itself, so the Pi's invocation would have benched the software rasterizer here.
#
# `--skip gles` is the interesting one, and it replaces a note that said this
# file would gain GLES rows once the account reached the `render` group. The
# account reached it on 2026-09-29, GLES now runs, and the rows are still not
# wanted -- for a different reason than before.
#
# Both backends report the device as `PowerVR B-Series BXE-4-32`, and they are
# not the same stack. Vulkan is Imagination's DDK (`libVK_IMG.so`). GLES is Mesa:
# `EGL_LOG_LEVEL=debug` shows the loader opening
# `/usr/lib/riscv64-linux-gnu/dri/pvr_dri.so`, Mesa's in-progress PowerVR
# Gallium driver, because `50_mesa.json` is the only EGL vendor on this image and
# there is no IMG GLES. So a `vulkan` and a `gles` row here would sit under
# identical device names while crossing a vendor boundary -- where on the Pi 5
# both rows are one Mesa. That is a comparison that looks like two backends and
# is really two drivers, and nothing in the file's own columns would say so.
#
# The numbers make the trap worse rather than better. Measured 2026-09-29, Mesa's
# GLES came in *faster* than the DDK's Vulkan on every row -- 57.9 ms against
# 64.0 on the full frame, 3.1 against 5.6 on the stroked path. It is also a
# different renderer backend, so that gap attributes to neither the driver nor
# the architecture, and the obvious reading of it would be wrong. Take these rows
# only with a question about Mesa's pvr driver specifically, and label them.
#
# Checked against three fresh runs on the board it came from, and `--check`
# passed three times over. The nine *device* rows hold to a third of a per cent
# or better, with one exception below -- tighter than the Pi 5 manages, because
# this board has no desktop running and one governor state.
#
# Two exceptions, both measured across those three runs rather than assumed, and
# both carrying a tolerance in the rows below:
#
#   `vulkan / frame, gradient ground` spread 1.6 per cent where every other
#   device row held under 0.4. Three of four runs agree at 43.15 and one came in
#   at 43.85, so it is an outlier rather than a distribution, and 2.0 covers it.
#   It is a single draw over every pixel, the most memory-bound row in the file.
#
#   Every `recording` row carries 5.0, matching the Pi 5's judgment on the same
#   rows. They spread up to 4.3 per cent here -- `stroked field` 4.3,
#   `distance field` 4.0, `tessellated, 4 samples` 2.9 -- because they are
#   sub-millisecond figures on a slow core, where a scheduler hiccup is a large
#   fraction of the measurement. An earlier sitting saw `recording / distance
#   field`, the row the bench itself marks noisy, move between 0.872 and 1.003.
#   Read that row as "about a millisecond" and not as three decimals.
#
# Worth knowing about the bar these tolerances sit under: `compare` only counts a
# row as regressed when it is *slower*, so a row that comes back faster than its
# tolerance never fails. Before the tolerances below were added, two recording
# rows did exactly that in one of the three checks -- `distance field` 1.1 per
# cent and `stroked field` 1.6 per cent under a one per cent bar -- and that
# check passed. A passing `--check` is therefore not evidence that a row is
# repeatable in both directions, only that it did not get slower.
#
# What this board is here to say, against `raspberry-pi-5-v3d.txt`: two tile
# architectures agree that the analytic field costs more than the triangles it
# replaces, and disagree about multisampling. The field is 2.6 times the
# tessellated fill here and 2.4 times on V3D; four samples cost 2.6 times one
# here and 1.2 times on V3D. `docs/on-a-board.md` has both tables and what
# follows from them.
#
# The frame is four rows rather than one as of 1ef0205, each adding one element
# to the one before, so a difference between two of them is what that element
# cost. Here the gradient ground alone is 43.1 ms of the 64.0 -- two thirds of
# the frame in one full-screen draw -- and the blurred layer is the next 15.3.
# The three cards and their shadows together are 5.6.
#
# A second frame joined this file on 2026-09-30: an interface's shape rather than a
# sampler of operations, and the only frame here with overdraw in it. Same conditions
# as the rows above -- desktop stopped, all four governors pinned, 50.1 C before and
# 53.1 C after, load 0.16, three runs and `--check` three times over. Every device row
# inside 0.06 per cent across the three.
#
#   stacked, wash            43.190   one axis-aligned gradient over the whole target
#   stacked, plus panels     74.078   a bar, a sidebar and a panel hiding 94.1% of it
#   stacked interface        93.966   eight list rows hiding most of the panel again
#
# **This is the frame that makes `non-parity.md` 21 worth something.** The three
# opaque rectangles add 30.888 ms while covering 94.1 per cent of the wash beneath
# them, so an opaque reordering that let them cull it would save about 40.6 ms of a
# 93.966 ms frame -- forty-three per cent. On `full frame, mixed content` the same
# arithmetic gives five, because three cards cover 6.6 per cent of that ground. The
# entry's value was never a property of the renderer; it was a property of what this
# bench happened to draw.
#
# It also gives `non-parity.md` 19 its case: the wash is vertical with its endpoints
# on the covered rectangle's edges, which is what upstream's `CanApplyFastGradient`
# requires, and nothing here had that before.
#
# One cross-check while the rows are new. `stacked, wash` is 43.190 and `frame,
# gradient ground` is 43.149 -- the same cost for the same kind of draw, one vertical
# and one diagonal, which says the second frame's wash is not doing something
# different from the first's.
#
# **One row above moved for a reason that is not the renderer, and it is recorded
# rather than tolerated.** `recording / stroked path` went 6.376 to 6.975 -- nine per
# cent -- when the stacked frame was added, and nothing about building a stroked path
# changed: `emblema-geometry/src/stroke.rs` is byte-identical across the commits, and
# the commit that moved it only *appends* loops to `gather` after the row is measured,
# so none of the new code has run by then. Interleaved on the board, alternating
# binaries in one session: 6.311, 6.993, 6.306, 7.012. On x86-64 the same pair reads
# 0.237 against 0.241, which is noise.
#
# So it is code layout. Adding a scene to `xtask/src/bench/frames.rs` shifted the
# stroker's hot loop in the binary, and on this board's in-order core that is worth
# nine per cent. What that says about the row is worth more than the row: **a
# `recording` figure here is measuring the binary's layout as well as the renderer's
# work**, so a move in one is not by itself evidence about the other. Bisect against an
# older binary on the board before believing one, which is what found this.
#
# The tolerance is left at 5.0 deliberately rather than widened to cover it. A layout
# shift is a step rather than noise, and the next one should fail this check and make
# somebody look, which is what this one did.
#
# The rows above the stacked ones were not re-recorded. They were measured again in
# the same run and came back 0.03 to 0.05 per cent higher, which is this board's
# run-to-run noise and not a change in what they measure -- writing those values in
# would have moved figures `on-a-board.md` derives from them for no reason. A row is
# re-recorded here when what it measures changes.
#
